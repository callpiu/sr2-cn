## 2. ★ 本轮新发现（有价值的副产物）

### 2.1 `juiced_CH.le_strings` 有确凿的越界 bug（但不是本问题）

```
juiced_CH         越界slot=22   maxslot=3491   ❌
patch_ch          越界slot=0    maxslot=0      (全ASCII，实为英文内容)
static_CH         越界slot=0    maxslot=2826   ✅
voice_script_CH   越界slot=0    maxslot=2826   ✅
platform_pc_CH    越界slot=0    maxslot=2826   ✅
```

- `maxslot=2826 = 2795+31`，**完美验证 slot=idx+32 规则**。
- `juiced_CH`（mod 的 OpenSpy 联网界面）用了一张 **≥3460 项**的字符表编码，
  而游戏加载的 `charlist_CH` 只有 2795 项 → **必然越界乱码**。
  - 对照 CZ：`h=1896 Zadej OpenSpy ID` → CH 应为 `输入 OpenSpy ID`
  - CH 实际：`[3481]傲 OpenSpy 卧[3254]`
- **这是 mod 作者自身的 bug，与"直升机突击活动字幕"无关。**
- 但它是"越界 slot → 乱码"的**活样本**，证明机制存在。

### 2.2 完整的 le_strings 格式（最终版，修正第六轮）

```
magic(4)=0xA84C7F73
ver(2) + buckets(2)
count(4)
[header 共 16 字节]
---- 桶表：从 0x10 起，buckets × 8 字节 ----
每桶 = <u32 record_offset> <u32 flag>
---- 记录偏移表：位于 16 + buckets*8，count × u32 ----
每个 u32 = 记录体的绝对偏移
---- 记录体 ----
<u16 hash> <u16 pad> UTF-16BE 文本 <u16 0>
unit<0x100 → ASCII直通; unit>=0x100 → slot=idx+32 → charlist_CH[unit-32]
```

`sr2strings.py` 的 `read_record` 布局**仍需按此修正**（当前假设 off+8/off+12，不匹配）。

### 2.3 引擎 loadcharlist@0x7F4430 的真实逻辑（栈偏移陷阱解析）

关键：`0x7F4607 mov ax,[esp+0x20]` 在 `add esp,0xc` **之前**执行，
此时 `[esp+0x20]` ≡ `sscanf` 的输出槽 `[esp+0x14]` = **读入的字符码**。
之后（`add esp`后）`[esp+0x20]` 才是 counter（初值0x100）。

```asm
sscanf(line, "%hu", &cp)        ; cp = 本行字符码
ax = cp                          ; (esp未变)
add esp, 0xc
cmp ax, 0x100
jb  → slot = ax                  ; 字符码 < 256 → slot = 字符码
jae → slot = counter; counter++  ; 字符码 >= 256 → slot = 计数器（从256起）
entry[0] = cp; entry[1] = slot
```
⇒ `slot = idx + 32` 对 charlist_CH 成立（224 项 ASCII 前缀）。**第六轮结论正确。**

### 2.4 语言码表（VA）

- 表 @ **0xDD1104**（VA）→ 文件偏移 0x9D1104
- `[0]=US [1]=ES [2]=IT [3]=JP [4]=DE [5]=FR [6]=NL [7]=SE [8]=DK [9]=CZ [10]=PL [11]=SK [12]=RU [13]=CH`
- 被 `loadcharlist` 内 10 处引用（0x3F443D/4477/47B5/4C7A/4D02 等）
- 语言码变量 @ **0xE8C470**（VA），初值 -1（未初始化时跳过 charlist 加载）

### 2.5 VA ↔ 文件偏移换算（重要！此前踩坑）

**ImageBase = 0x400000**，`.text`/`.rdata` 段 VA==FO，故：
```
文件偏移 = VA - 0x400000
```
（第六轮把文件偏移当 VA 用，导致 0xDD1104 读出全 0）

## 6. 教训

1. **"静态全绿 ≠ 能跑"** 再次应验：所有静态证据都正确，实机仍乱。
2. **VA/文件偏移必须换算**（ImageBase=0x400000），否则读出全 0 还以为数据不对。
3. **反汇编要看 esp 变化**：`add esp,N` 前后的 `[esp+X]` 是不同变量。
4. **乱码字是人工辨认的，可能认错** —— 下一轮应以运行时内存为准，不再依赖截图辨认。

## 一、本轮最重要的结论

```
实测：把 static_CH 里两条字幕记录的槽位全部改成 ASCII（AAABBBCCC...）
      游戏里字幕【仍然乱码】，一字未变

=> 引擎【不读】patch.vpp_pc 里 static_CH 的这两条记录
```

### 这推翻了前一轮的前提

前一轮的「图集法」之所以有效，是因为它改的是**图集**（`fnt_chinese.g_peg_pc`），
而**不是** `static_CH`。图集是共享的，所以改图集能影响显示；改文本不能。

**所以「改文本」这条路（前一轮 §5 的正确路线）前提不成立。**

### ASCII 探针的方法学说明

我这次把槽位设成**纯 ASCII 码点**（A=65, B=66…），
因为 `charlist_CH` 前 32 项就是 ASCII 原样（索引 = 码点）。
把记录解码成 `AAABBBCCCDDDEEEFFFGGG` 后回读验证通过。

**屏幕没有任何变化** —— 这是最干净的「文本层无效」证据。

## 二、本轮建立的新工具

### 2.1 `_N1_digitprobe.py` ★ 数字探针

**思路**：把图集格子里的字形替换成「该格编号」的数字图。
因为 `屏幕显示 = charlist[E(c)+5]`，所以被探测字符 c 显示出来的就是 `E(c)` 的数值 ——
**一张截图读出几十个 E 值，不需要认字**。

```bash
# 把格 k_start..k_end 换成数字图
python _N1_digitprobe.py make <vpp> <k_start> <k_end> <out_vpp>

# 把字幕记录改成候选字序列
python _N1_digitprobe.py text <vpp> <chars> <out_vpp>
```

内含 5×7 点阵字体（数字 0-9 + `#` + `-`），以及 DXT3 块重编码。

### 2.2 `_N6_buildtextfix.py` 文本替换修复器

按 `pairs.json` 的映射表替换 `static_CH` 记录的槽位。
（**本轮已证明无效**，但代码本身正确，可留作其它用途。）

### 2.3 `_N8_engine_would_draw.py` 图形判定器

从图集裁出「引擎实际会画的格子」，输出 PNG。
**不需要进游戏就能看到会显示什么** —— 用来验证修复是否正确。

## 三、本轮验证/推翻的假说

| 假说 | 结论 | 依据 |
|---|---|---|
| `E(c) = 码点排名 - 5` | ❌ 推翻 | 原版命中 1/23 |
| `E(c) = charlist索引 - 5` | ❌ 推翻 | 原版 1/23，简体 0/19 |
| `E` 按 GBK 排序 | ❌ 推翻 | 0/23、0/19 |
| `E` 按 Big5/cp950 排序 | ❌ 推翻 | 0/23、0/19 |
| `E = 原版繁中 charlist 索引` | ❌ 推翻 | 强检验 0/12 |
| 简体表 = 原版表的重排 | ❌ 推翻 | 共有 1668 字，顺序一致但字集不同 |
| `static_CH` 有重复 hash | ❌ 无 | 12250 条全唯一 |
| **改 `static_CH` 文本能修好字幕** | ❌ **推翻** | **ASCII 探针无效** |

### 实测到的 E 差值（无任何规律）

```
原版:  E - clist_idx ∈ {+0,+1,+2,+3,+4,+5, -3,-9,-10,-11,-16,-21}
简体:  E - clist_idx ∈ {-2060,-1676,-1037,-625,-500,-52,-46,-37,-35,-28,-23,-11,
                        +30,+115,+134,+545,+742,+1152,+1764}
```

**结论：`E` 无法用任何排序/编码/索引公式推算，必须实测。**

## 五、当前状态的逻辑矛盾（留给下一位）

```
事实 A：改 fnt_chinese.g_peg_pc（图集）→ 字幕显示会变（前一轮验证过）
事实 B：改 static_CH 的槽位（含纯 ASCII）→ 字幕显示【完全不变】

如果引擎读 static_CH 并用它取槽位：
    A 成立（图集变了字形就变）
    B 也应该成立（槽位变了取的字就变）  ← 但实测不成立

=> 引擎取文本的来源【不是】patch.vpp_pc 的 static_CH
   但它取【字形】用的是 fnt_chinese 图集

可能的解释
    1. 有另一份 static_CH 在别处（未找到）
    2. 引擎把字符串表【缓存】在别的地方（如存档、注册表、临时文件）
    3. 活动字幕用的是另一套机制（如 .xtbl 里直接写文本，或 Lua 拼接）
    4. Juiced 拦截了 static_CH 的读取并从别处提供数据
```

## 六、下一步建议（优先级排序）

### 1. 用数字探针确认「引擎到底读不读 static_CH」

```
a) 备份 patch.vpp_pc
b) python _N1_digitprobe.py make patch.vpp_pc 366 375 probe.vpp_pc
   （把格 366..374 换成数字）
c) 把 probe.vpp_pc 里的 0x84F287ED 记录槽位改成「你的弟兄们…」原槽位
d) 进游戏看字幕
   如果显示数字   -> 引擎读 static_CH，且 E(你) 落在 366..374 区间
   如果仍乱码     -> 引擎不读 static_CH（与本轮 ASCII 结论一致）
```

**这是最省事的一步 —— 一个探针同时回答「读不读」和「E 是多少」。**

### 2. 用 Process Monitor 抓文件读取

```
过滤: Process Name = sr2_pc.exe, Path 含 "static" 或 "le_strings"
```
能直接看到引擎读了哪个文件、哪个偏移。

### 3. 用 x32dbg 对字符串表内存下断点

前一轮已定位到内存里的 le_strings 表：
```
@0x1FE5598  和  @0x2057F4C
记录格式: [hash1:4][hash2:4][长度:4][槽位流][00 00]
目标记录槽位流: B5 01 E2 03 86 01 ...
```
对那个地址下**硬件读断点**，追到调用栈。

### 4. 检查 Juiced 是否接管了字符串加载

```
Juiced 源码在 F:\sr2-cn\juicedsrc\Saints-Row-2-Juiced-Patch-main\
搜索: le_strings / static / charlist / LoadString
```

### 5. 直接问那位接手人

他的文档说「图集法有效」—— 说明他见过字幕变化。
**他可能已经知道正确的文本来源**，只是没写进文档。

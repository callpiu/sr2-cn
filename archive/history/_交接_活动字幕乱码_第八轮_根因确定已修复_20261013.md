## 1. ★★★ 根因（一句话）

**`patch.vpp_pc` 里的 `charlist_CH.txt` 被删掉了 `count=N` 头行。**

引擎 `loadcharlist@0x7F4430` 必须用 `sscanf(第一行, "count=%u", &count)` 取得字符表项数；
当前文件第一行是 `32`（不是 `count=2795`）→ **匹配失败 → count 保持 0**
（`0x7F4587 xor ebx,ebx` + `0x7F458A mov [esp+0x1c],ebx` 恰好把 count 槽清零）
→ `malloc(0)` → 循环 0 次 → **字符表为空** → 所有中文按"缺表"路径渲染 → **乱码**。

**这完美解释了此前的核心矛盾：磁盘数据解码完全正确，实机却乱码。**

## 2. 证据链（完整闭环）

### 2.1 反汇编 `loadcharlist@0x7F4430`（VA，ImageBase=0x400000）

```asm
0x7F457D  lea ecx, [esp+0x10]      ; &count
0x7F4581  push ecx
0x7F4582  push 0xE26080            ; "count=%u"
0x7F4587  xor ebx, ebx
0x7F4589  push esi                 ; 文件首行指针
0x7F458A  mov [esp+0x1C], ebx      ; ★ 把 count 槽(=add esp 后的 [esp+0x10])清零
0x7F458E  call 0xC97089            ; sscanf(line, "count=%u", &count)
0x7F4593  mov edx, [esp+0x1C]      ; (esp未变) edx = count
0x7F4597  add esp, 0xC
0x7F459B  lea eax, [edx*4]
0x7F45A8  call 0xC00DB0            ; malloc(count*4)
...
0x7F45E7  mov [esp+0x20], 0x100    ; slot 计数器 = 256
0x7F45F1  cmp ebx, [esp+0x10]      ; ★ 循环上限 = count
0x7F45F5  jae 0x7F465E             ; count=0 → 直接结束，表为空
```

**⇒ count=0 时字符表完全不加载**（对应第四轮实测 `num_cchars=0`）。

### 2.3 为什么是 2795 而不是官方的 2838

实测 `static_CH / voice_script_CH / platform_pc_CH` 的 **slot 最大值 = 2826**，
而 `slot = idx + 32` ⇒ 最大 idx = **2794** ⇒ **表就是 2795 项**。

（若按官方 2838 项编，最大 slot 应为 2869；实测 2826 ⇒ **文本是按 2795 项表编的**。）

⇒ 因此 `count=` 必须填 **2795**（与数据体一致），**不能**填 2838（会越界读）。

## 6. 教训（重要）

1. **"静态全绿 ≠ 能跑"** 的教科书案例：解码器不依赖 `count=`，所以解得完美；
   **引擎依赖 `count=`**，所以跑起来乱。**必须按引擎的解析逻辑验证文件格式。**
2. **不要假设文件格式"看起来对"就行** —— 要逐字节对照官方原版。
3. 此前的 `juiced.ini ForceLanguage`、`common/textures.vpp_pc` 替换**全是错的方向**，
   已于本轮/上轮回滚。
4. `sr2lib.py` 的模块注释里其实**早就写明**了正确格式
   （`header comment, "count=N", then N decimal codepoints`）—— **先读项目自带文档**。

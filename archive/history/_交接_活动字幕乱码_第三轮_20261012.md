## 三 · 一个反直觉的重要观察（**关键线索**）

```
同一个活动 HUD 上：
  ✓ 顶部活动框「直升机突击 / 已完成停靠 / 面包车耐久 / LVL2」 -> 全部显示【正确】
  ✗ 底部字幕「任璨偶巧位校衡…」                              -> 【乱码】
```

**同一个界面、同一时刻、同一个字体**，一部分中文正确、一部分乱码。

这排除了：
- 字体缺字（乱码字都是合法汉字，不是豆腐块）
- 字体图集损坏
- 语言/字表加载错误

**说明乱码只发生在【特定的字符串解析/渲染路径】上**，
最可能是这条字幕走了**富文本 `[format]` 或 `[color]` 标签解析**，
而标签解析器在某种条件下把后面的字符索引算错了。

### 支持这个判断的证据

```
REC1 (hash 0x84F287ED) 磁盘内容:
    [format][color:green]弟兄们[/format]需要你的保护
REC2 (hash 0x10AF1E62) 磁盘内容:
    [format][color:green]弟兄们[/format]要出去谈几笔生意，保护他们免遭袭击

用户看到的 22 字，与 REC2 的【中文字符数完全一致】(22)
```

**但改了这两条记录屏幕没反应** -> 说明屏幕用的不是这两条
（或者是同一个 hash 在**别处还有一个定义**，我还没穷尽所有容器）。

## 四 · 下一步建议（按优先级）

### 步骤 1（最值得做）：穷尽**所有容器**里的这两个 hash

目前只查了 `patch.vpp_pc`、`DLC/Text/*`、`Mods/JUICED - Strings/*`、exe、DLL。
还没查的容器：

```
common.vpp_pc        (6166 条目)
city_load.vpp_pc     (624)
chunks1..4.vpp_pc
anims / audio / hmaps / meshes / music1..4 / pegs / textures
DLC/ 下的其他 .le_strings（已查 DLC/Text/，还有 DLC/*/Text/ 子目录？）
```

**做法**：写一个脚本，遍历**所有** vpp 的所有条目（含无扩展名的），
用 `file_offsets + read_units` 尝试解析，找 hash 命中。

（注意：用 `sr2lib.Vpp` 打开 `textures.vpp_pc`（1.26 GB）会爆内存，
 要用「只读文件头 + entry 表 + seek」的轻量法。）

### 步骤 2：确认这条字幕的**显示条件**

截图显示的是「已完成停靠 0/4」阶段。
请问用户：**这条字幕是什么时候出现的？**

```
□ 活动一开始就出现？
□ 每次停靠成功后出现？
□ 只在某个特定阶段出现？
□ 一直显示？
```

如果能确定触发时机，可以对照活动定义的 xtbl / chunk 反查。

### 步骤 3：用 Cheat Engine 之类工具**内存搜索**

既然乱码字不存在于磁盘，那它在**内存里**。
用 Cheat Engine 搜「任璨偶巧」的 UTF-16LE 字节，
找到内存地址后即可反查它从哪个模块/资源加载。

**这是唯一能一锤定音的方法。**

### 步骤 4：换一条字幕做探针

不要再假设是这两条。把 `static_CH` 里**任意一条会被活动 HUD 显示的记录**
（例如活动目标文本）改掉，看屏幕有没有反应 —— 用来验证
「改 static_CH 能否影响活动 HUD」这个基本前提。

**如果连这个都不生效**，说明活动 HUD 的文本根本不走 `static_CH`，
那就该去查 chunk 或 Juiced 的 API 层。

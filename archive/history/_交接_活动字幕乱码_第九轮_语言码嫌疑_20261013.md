# 活动字幕乱码 · 第九轮：count= 修复实测无效 → 静态证据全面转向「语言码 / 表加载」

**日期**：2026-10-13（第九轮）
**触发**：用户实测反馈 **"还是没有变化"**（已部署 `count=2795` 的 charlist_CH）
**本轮结论**：`count=` 方向在**格式上是对的**（与官方同构），但实测无效 ⇒
**引擎极可能根本没走到"解析 charlist"这一步**。新证据强烈指向 **语言码 `[0xE8C470]` 不是 13(CH)**，
或 **`charlist_CH.txt` 打开失败**。

## 1. ★ 本轮最重要的新证据：exe 语言白名单里「没有 CH」

反汇编 exe 的语言初始化函数（VA `0x51F440` 一带）：

```asm
0x51F481  cmp  byte [0xE9A2E0], bl      ; "语言已设置"标志
0x51F487  je   0x51F4F5                 ; 未设置 → 整段跳过
0x51F489  mov  eax, [0xE9A2DC]          ; 语言字符串指针
0x51F48E  cmp  eax, ebx
0x51F490  je   0x51F4F5
0x51F492  cmp  byte [0x2528B0F], bl     ; 字体已初始化？
0x51F498  jne  0x51F4F5                 ; 已初始化 → 跳过（只跑一次）
0x51F49C  push eax                      ; = 语言字符串
0x51F49D  push 0xE260F8                 ; ★ "US DE ES FR IT NL SE DK CZ PL JP SK RU"
0x51F4A2  mov  dword [0xE8C470], -1     ; 先置 -1
0x51F4AC  call 0xC96870                 ; ★ strstr(whitelist, lang)
0x51F4B4  test eax, eax
0x51F4B6  je   0x51F4E6                 ; 不在白名单 → 保持 -1
0x51F4C0  mov  eax, [esi*4 + 0xDD1104]  ; 语言表[esi]
0x51F4C8  push edi
0x51F4C9  call 0xC99030                 ; strcmp
0x51F4D8  cmp  esi, 0xE                 ; 14 项
0x51F4DD  or   esi, -1                  ; 没找到
0x51F4E0  mov  [0xE8C470], esi          ; ★ 写入语言码
0x51F4E6  cmp  dword [0xE8C470], -1
0x51F4ED  jne  0x51F4F5
0x51F4EF  mov  [0xE8C470], ebx(0)       ; ★ 兜底：强制 0 = US
```

**核心事实：**
- 白名单串 `0xE260F8` = `"US DE ES FR IT NL SE DK CZ PL JP SK RU"`
  → 13 个 token：**US / DE / ES / FR / IT / NL / SE / DK / CZ / PL / JP / SK / RU**
  → **★ 没有 `CH`，也没有 `EN`（注意首项是 `US` 不是 `EN`）**
- 语言表 `0xDD1104` 14 项 = US ES IT JP DE FR NL SE DK CZ PL SK RU **CH**（`[13]=CH`）
- 匹配失败 → `[0xE8C470] = -1` → 再被兜底强制为 **0（US）**

⇒ **如果最终语言码是 0(US)，`loadcharlist` 会去开 `charlist_US.txt` —— 而这个文件根本不存在！**

**已核实 `patch.vpp_pc` 里的 charlist（两个版本都查了）：**
```
charlist_CH.txt  charlist_CZ.txt  charlist_JP.txt  charlist_PL.txt
charlist_RU.txt  charlist_SK.txt  JPCharList.txt
（没有 US / EN / DE / FR / ES / IT / NL / SE / DK）
```

## 2. ★ loadcharlist 的完整「跳过整张表」条件

```asm
0x7F444A  mov  eax, [0xE8C470]
0x7F444F  cmp  eax, -1
0x7F4455  je   0x7F4688                 ; ★条件① 语言码 == -1 → 不加载
...
0x7F447C  push "charlist_%s.txt"
0x7F448D  call vsprintf
0x7F4499  call 0xBFD880                 ; 打开/初始化文件对象
0x7F44A3  je   0x7F4688                 ; ★条件② 打开失败 → 不加载
...
0x7F4550  cmp  byte [esi], 0x2F         ; 跳过所有 '/' 开头的行
0x7F457D  lea  ecx, [esp+0x10]
0x7F4582  push "count=%u"
0x7F458E  call sscanf                   ; ★ 取项数
0x7F45A8  call malloc(count*4)
0x7F45F1  cmp  ebx, [esp+0x10]          ; 循环上限 = count
```

**⇒ 我的 `count=2795` 修复在格式层面完全正确（与官方 `count=2838` 同构，仅数值不同）。**

## 3. ★★ DFEngine 不写 `[0xE8C470]`（`ForceLanguage` 是死键）

- 全镜像搜 `0xE8C470`：**仅 1 处引用**，且是 `cmp byte [0xe8c470], 0`（**只读**）
- DFEngine 的 `ForceLanguage`（fo `0x18A240`）只是 **ini 键名/注释表**里的一项：
  - `0x18A212` = `"EN,DE,FR,ES,IT,NL,SE,DK,PL,CZ,RU,CH,JP"`（注释）
  - `0x18A233` = `"NA"`（默认值）
  - 这些字符串**没有任何代码引用**（搜到的"引用"其实是 .rdata 里的重定位数据）
- **⇒ `juiced.ini ForceLanguage=CH` 根本不会写进 `[0xE8C470]`**
  ⇒ 所以第四轮改它「无效」是**必然的**，不是巧合。

**一次性读取：**

- **B** 字体初始化标志 `[0x2528B0F]`
- **C** 运行时字符表 `[0x2528B2C]` 指针 / `[0x2528B30]` 项数

  - ASCII 前缀是否 224？

- **D** 内存中是否有「正确中文」/「乱码中文」的真 Unicode

**判读表：**
| 观察 | 结论 | 对策 |
|---|---|---|
| 语言码 = -1 | 引擎从未初始化语言 | 部署 exe 补丁 `_SR2_pc_exe_forceCH.exe` |
| 语言码 = 0 (US) | 被白名单强制成 US → 找 `charlist_US.txt`（不存在） | 同上（或补 `charlist_US.txt`） |

| cc_cnt = 0 或异常 | 表加载失败 | 查 `0xBFD880` 文件打开路径 |

## 9. 教训（累计）

1. **"静态全绿 ≠ 能跑"** —— 解码器与引擎的解析逻辑必须分别验证
2. **VA/文件偏移换算**：ImageBase=0x400000 ⇒ 文件偏移 = VA − 0x400000
3. **反汇编要看 `add esp,N` 前后的栈偏移**（不同变量）
4. **改 ini 前先确认有没有代码引用该键**（DFEngine 的 `ForceLanguage` 就是死键）
5. **★ 新：先确认"哪个 patch.vpp_pc 版本在生效"**——本项目的 v415(712) 与 build(715) 是两套谱系
6. **乱码字是人工辨认的，可能认错** —— 以运行时内存为准

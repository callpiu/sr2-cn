## 1. 问题定义

《Saints Row 2》简体汉化补丁中，「直升机突击（Helicopter Assault）」联机活动第二级的任务提示字幕乱码。
**单机与联机都出现**。原英文：
- `Your homies need your protection`（串 hash `0x84F287ED`）
- `Your homies are heading out on some deals, protect them from attackers`（串 hash `0x10AF1E62`）

用户实测乱码字面：
- REC1：`任璨偶巧位雄衡任璨伪该`
- REC2：`任璨偶巧位校衡勾远藐乱携 伪该亡位通像匪冰挺拮`（"携 伪"间的空格疑为渲染痕迹）

## 2. 已确认事实（本会话重新验证，全部有脚本证据）

### 2.1 数据位置与内容（静态数据是正确的！）
- 两个 hash **只存在于 `static_CH.le_strings`**（platform_pc_CH / voice_script_CH 均无），即活动文本数据源就是 static_CH。
- 干净 v532 中解码结果（用 charlist_CH）：
  - REC1 = `你的[format][color:green]弟兄们[/format]需要你的保护`（11 个 CJK）
  - REC2 = `你的[format][color:green]弟兄们[/format]要出去谈几笔生意，保护他们免遭袭击`（22 个 CJK）
- 当前部署（build_fix，标签已删）：
  - REC1 = `你的弟兄们需要你的保护`
  - REC2 = `你的弟兄们要出去谈几笔生意，保护他们免遭袭击`
- **结论：磁盘上的字符串数据完全正确（是通顺中文），乱码发生在「渲染期」**——即字形索引被错误映射。

**⚠️ 未解异常（重要）**：
1. 同一索引在不同串/不同位置渲染成不同字（要→衡 vs 校；保→伪 vs 亡；护→该 vs 位；们→位 vs 像）。这**不是**一个静态双射——要么用户抄录有误/有错位，要么渲染与上下文（位置/颜色段）相关。
2. **关键线索**：`们`(332) 在绿色字段「弟兄们」渲染成「位」，在黑色字段「他们」渲染成「像」→ **绿色文本与黑色文本可能使用不同字体/字表**（若乱码是在带 `[color:green]` 标签的版本上观察到的）。这一点尚未验证，但是重要侦查方向。

## 4. 字体系统全貌（两套中文字体，都叫 fnt_chinese）

### 4.1 patch 字体（游戏大部分中文 UI 用这个，渲染正确）
- `patch.vpp_pc` 内：`fnt_chinese.vf3_pc`（2795 字形，67268 B）+ `fnt_chinese.g_peg_pc`（2048×2048 DXT3 图集，4194304 B）
- 配套 `charlist_CH.txt`（2795 项）——**字形顺序 = charlist_CH 索引**，所以渲染正确。

### 4.2 common 字体（活动 HUD 疑似用这个，渲染错乱）
- `common.vpp_pc` 内：`fnt_chinese.vf3_pc`（**2838** 字形，68300 B）
- 图集在 `textures.vpp_pc` 内：`fnt_chinese`（**扩展名为空**，body 偏移 **85407184**，4194304 B，2048² DXT3）
- **无配套 charlist 文件**（全盘扫描无 2838 项字表）。
- 网格实测（ink 投影自相关）：**patch 列距=31px；common 列距=30px、行距≈31px**（origin 约 x=2,y=34，每行 66 个）。两图集字型明显不同。

### 4.3 vf3 / le_strings 格式速查（接手必备）
- **static_CH.le_strings 头**：`<IHHI>` = magic(u32=0xA84C7F73) + ver(u16) + buckets(u16=1024) + count(u32=12250)，共 12 B；随后 `buckets×(cnt u32, addr u32)` 桶表 + `count×u32` 指针表（记录绝对偏移）；记录 = `[id1 u16 LE][id2 u16 LE][slots u16 **BE** …][0x0000]`；文本从 `off+4` 开始；hash=`(id1<<16)|id2`。
- **charlist_CH.txt 格式**：无 `count=` 头，就是**一行一个十进制码点**，从 32（空格）开始，94 个 ASCII 在前，CJK 从索引 94 起。
- **VPP**：`S.Vpp(path)` 会 `open().read()` 全文件——**绝不能用它打开 textures.vpp_pc（1.26 GB）/ chunks\*.vpp_pc**；用「只读文件头 + entry 表 + seek 单条目」的轻量读取法（参考 `tex_find.py` / `match_grid3.py` 里的 `hdr()` 函数）。

## 5. 修复候选方案（按推荐度排序）

### 方案 A：把活动 HUD 的字体绑定改成 patch 字体（最干净，待验证）
- 思路：活动 HUD 之所以乱，是因为它用了 common 字体（字表顺序与 charlist_CH 不一致）；若能让它改用 patch 字体（顺序一致），直接修好。
- 待查：活动 HUD 的字体名在哪个 xtbl 里指定。候选文件：`activity_player_persona_replacement.xtbl`、`helicopter_test.xtbl`、`multiplayer_mode_*.xtbl`、`game_globals*.xtbl`、以及 DFEngine.dll 内硬编码。做法：grep 各 xtbl 内容里的 `fnt_` / `font` 引用。
- 风险：可能硬编码在 exe；改动影响面未知。

### 方案 B：重映射活动串的 slot 到 common 字体的字形索引（最局部，被阻塞）
- 思路：对每个目标字，找到它在 common 图集里的 cell 索引，slot = cell+0x20。
- **阻塞点**：需要完整的 common 字表（cell→字符）。像素匹配已失败（字型不同）。需要换方法：
  - (i) 用 OCR/字形识别库识别 common 图集每个 cell；
  - (ii) 找到 common 字体真正配套的 2838 项字表（也许在 JP 语言包 / sr2orig 原版补丁 / 游戏 exe 里，尚未穷举）；
  - (iii) 从游戏反推（见方案 D 的实验结果直接测出置换）。

### 方案 C：用 patch 图集覆盖 common 图集（有前提，当前不成立）
- 思路：textures.vpp_pc 的 `fnt_chinese` 换成 charlist_CH 顺序的图集。
- **前提不满足**：两图集网格不同（31 vs 30px），直接覆盖会错位。需要先把 patch 图集重采样到 30px 网格，并处理 2838 vs 2795 字形差；且会影响所有用 common 字体的界面（影响面未知，风险中高）。

### 方案 D（强烈推荐的第一步）：实机受控实验，直接测出精确置换
- 思路：把 REC1/REC2 改成一个**精心设计的测试串**（如包含一串连续 charlist_CH 索引 `啊阿埃挨…` 或直接 `0123456789` 对应索引），进游戏截图，即可**无歧义地读出** HUD 的真实索引→字形映射，一举解决 2.2 的所有冲突（转录误差/上下文依赖/绿黑字体差异）。
- 建议测试串：选 20~30 个 charlist_CH 里互不相同的常用字，等长替换 REC1（注意 le_strings 只能等长替换；长度不够可用空格 slot 0x20 补齐……注意 ASCII 空格 slot=0x20+0=0x20，CJK slot=idx+0x20）。
- 这一步能同时验证「绿/黑不同字体」假设：把测试串分别放进绿色段和黑色段对比。

### 3.2 渲染层（关键发现）

```
① exe 的 D3DXCreateFontA 导入项：
   IAT 槽 VA = 0x00DB8418
   ★ 整个 exe 里【零引用】—— 导入了但从不调用！

② DFEngine.dll（游戏渲染引擎）：
   导入 GDI32 仅 BitBlt，USER32 无文本函数
   ★ 没有任何文本渲染 API！

③ hud_msg.lua 第 104-106 行：
   vint_set_property(o, "font", "thin_overlay")
   ★ thin_overlay -> (fnt_body_n, fnt_body_s)，两者 N=224（仅 ASCII）
```

### 3.3 矛盾点

```
面板文字（直升機攻擊 / 阻止行動 / 箱型車耐久度）→ 正确显示繁中 ✓
字幕文字（兄弟們需要你的保護）              → 乱码 ✗

同一个 charlist_CH，同一个 fnt_chinese 图集
=> 说明【字幕走了一条独立的、有缺陷的渲染路径】
```

## 六、下一步的可能方向

### 方向 A：hook 真正的文本绘制函数（工作量大）

游戏的文本不走 D3DX、不走 GDI。需要：

1. 用 x32dbg 在游戏里对字幕文本的 UTF-16 字节下**硬件访问断点**
   ```
   乱码2 的 UTF-16LE:
   7F 4F 7C 76 49 51 48 5F 1F 50 65 6B A9 5F CB 53
   14 90 A2 87 A4 4E 1F 66 DE 9E F1 4F 98 8A D9 4E
   5E 90 68 51 E5 53 5D 52 3E 65 CB 64
   ```
2. 命中的调用栈就是真正的绘制函数
3. hook 它，替换字符串

### 方向 B：hook Direct3D 层的顶点/纹理提交

hook `IDirect3DDevice9::DrawIndexedPrimitive`，在字幕绘制时替换纹理坐标。
技术难度高。

### 方向 C：换字体但保持数据不变

如果字幕用的字体是 `fnt_korea`（1424 项韩文）之类的字体，
它恰好含部分汉字，导致显示错误字符。

**验证方法**：hook `D3DXCreateTextureFromFileInMemory`（游戏确实导入且可能使用），
记录字幕绘制前最后一次加载的纹理名。

### 方向 D：接受现状

这是 2009 年游戏的官方 CJK 缺陷，官方繁中版就有。

## 九、核心教训

1. **`regsvr32 exit=3` 会误导** —— 那只是找不到 `DllRegisterServer`，
   不代表 DLL 加载失败。用 `rundll32` 验证。

2. **手工构建 PE 极其困难** —— 我花了大量时间写 COFF→PE 链接器，
   产出的 EXE/DLL 都无法运行。**直接用 zig**。

3. **ASCII 探针是最强的验证手段** —— 比改槽位、改字体都干净。
   这次它一举证明了 `static_CH` 不是字幕来源。

4. **不要假设 API 被使用** —— `D3DXCreateFontA` 被导入但零引用。
   必须验证 IAT 引用。

5. **CJK 位图诊断要小心** —— 我一度把「兄弟們」误读为「光彈借」，
   导致后续推导全错。

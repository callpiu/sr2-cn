# Saints Row 2 中文字幕乱码 —— 交接文档（最终版）

> ## ★★★ 2026-10-17 04:02 重大更正：真正的根因已找到 ★★★
>
> **本文档 §1~§4 的「根因 = 图集字形顺序与 charlist 差 5」是错的**（那是被错误字体表误导出的假象）。
>
> **真正根因：游戏缺装 `common.vpp_pc`（汉化包的「字体表修复」）。**
>
> - 引擎加载的中文字形表是 **`common.vpp_pc` → `fnt_chinese.vf3_pc`**，不是 `patch.vpp_pc` 里那张
> - 官方版这张表 **N=2838，U 数组其实是「字距/kerning」**（U 唯一值 302 个、间隔 1~8 杂乱）
> - 汉化版这张表 **N=2795，U 唯一值 65 个、间隔恒为 31** —— 这才是真正的**图集列坐标**
> - 引擎拿「字距」当「列坐标」→ 每个字都取到错误位置 → 全部乱码
>
> 汉化补丁 v10 的 README 里写得很清楚（「修复 2：common.vpp_pc → fnt_chinese.vf3_pc 换表」），
> 而本机游戏目录里 `common.vpp_pc` 是**官方原版**（`f041934f…`）→ 缺了这一半。
>
> **已修复**：把汉化包的 `common.vpp_pc`（`65dbcbec…`）装进游戏，vf3 表 md5 变为
> `dd72f198…`（与 `patch.vpp_pc` 里那张完全一致 ✓）。
>
> 因此：**§3「修复手法」里那套「搬图集字形」的做法不要再用了** —— 它是在补偿错表，
> 而且会顶坏共用同一格的常用字（`任务`→`你务`）。装对表即可，零副作用。

## 一、问题定义

「直升机突击」活动的中文提示字幕乱码，两句：

| 记录 ID | 简体汉化版文本 |
|---|---|
| `84F287ED` | 你的弟兄们需要你的保护 |
| `10AF1E62` | 你的弟兄们要出去谈几笔生意，保护他们免遭袭击 |

原版（繁体）对应记录文本为 `你的兄弟們需要你的保護` / `你的兄弟們正要去進行交易，保護他們避免受到攻擊`。

**这是官方 bug**：不打汉化补丁、用繁体玩，同样乱码（用户确认）。

## 二、已确认的技术事实（全部逐格/逐字节验证过）

### 2.1 字体三件套（都在 `patch.vpp_pc`）

| 项 | 说明 |
|---|---|
| `charlist_CH.txt` | 字符表。十进制码点、换行分隔。原版 **2838** 项；汉化版 **2795** 项 |
| `fnt_chinese.vf3_pc` | 坐标表。`VFNT` + ver=2 + N@0x08 + 头 0xD0 + N×16 记录 + **U 表@(0xD0+N×16)** + V 表紧随其后（**可能被截断**，原版缺 5 项） |
| `fnt_chinese.g_peg_pc` | 图集。4194304 B = **2048×2048 DXT3**；原始版另在 `textures.vpp_pc` → `fnt_chinese` |

### 2.2 关键换算（此前长期卡住的点）

```
vf3 的 (U[k], V[k]) 就是图集第 k 格的左上角像素坐标     ← 逐格视觉验证
格子 31×31，字形墨迹约 22×22 居中
图集第 k 格装的字形 = charlist_CH[k + OFFSET]，OFFSET = 5   ← 原版/汉化版都是 5
```

### 2.3 乱码机制

```
引擎把字符 c 映射成索引 E(c)  →  取 atlas[E(c)]  →  画出该格字形
显示出来的字 = charlist_CH[ E(c) + 5 ]
```

- `E` **不等于** `charlist_CH.index`，也不等于任何随包 charlist 的顺序 —— 它是引擎自己的一张表 `M`
- 实测（原版）：`E(你)=331`、`E(的)=1779`、`E(兄)=405`、`E(弟)=962` …（`charlist.index` 分别是 333/1787/405/962）
- **★ `M` 有碰撞**：多个字符映射到同一个 `E`。实测 **`E(你) = E(任) = 331`**

### 2.4 le_strings 格式

```
@0  magic 0xA84C7F73
@4  ver u16
@6  buckets u16
@8  count u32
@12 bucket 表（buckets×8：count u32 + offset u32）
@12+buckets*8  pointer 数组（count×u32 绝对偏移）
记录 = [id1 LE u16][id2 LE u16] + 大端 u16 槽位流 + 0x0000
槽位 = charlist 索引 + 0x20
```

**ID 字节序陷阱**：文件前 4 字节 = 目标 hash 的 4 字节**两两 swap**。
例：`84F287ED` → 文件里是 `F2 84 ED 87`。

## 三、修复手法（已验证有效）

对每个乱码字 `c`（截图里看到它被显示成了 `d`）：

```
源格 src = charlist_CH.index(c) - 5      ← 这一格装着 c 的正确字形
目标格 dst = charlist_CH.index(d) - 5     ← 引擎实际取用、装着错字的那一格（= E(c)）
把 src 格的 31×31 像素搬进 dst 格，只重编受影响的 DXT3 块
```

**不需要知道引擎为什么取错格子，也不需要改 vf3（格子坐标不变）。**

### 实测结果

| 版本 | 状态 |
|---|---|
| **原版（繁体）** | ✅ 两句字幕恢复正常（用户确认） |
| **简体汉化版** | ✅ 第 1 句全对、第 2 句只剩结构性缺失（用户确认「和你预期的一样」） |

## 四、★ 致命副作用（当前唯一障碍）

**因为 `M` 有碰撞，把字形搬进图集格子会顶掉「原本正确的那个字」。**

实测现象：修好后，游戏里 `任务` 全部变成 **`你务`** —— 因为 `任` 和 `你` 共用格 331，我把格 331 换成 `你` 的字形后，`任` 跟着变成 `你`。

**影响面**：凡是「被顶字」（任、交、位、雄、伪、该、亡、远、乱、冰、挺…）在游戏别处都会跟着坏。
汉化版 19 对里十几个被顶字都是常用字，所以副作用严重 —— **已全部回退**。

> 原版那次修复很可能也有同样问题（用户当时只验了那两句字幕）。重做时要一并考虑。

## 五、正确的路线（下一步，待实施）

**不动图集，改文本。** 原理：把「错位」提前在文本里补偿掉。

对文本里的每个字符 `c`，找一个字符 `c'` 满足：

```
E(c') = charlist_CH.index(c) - 5
即  c' = M[ charlist_CH.index(c) - 5 ]
```

然后把记录里 `c` 的槽位换成 `c'` 的槽位。

- **完全不碰图集 → 零副作用**
- 槽位 = charlist 索引 + 0x20，可直接改 le_strings

### 拿 `M` 的办法：探针版

把一条字幕记录改成「一串候选字」，进游戏截一张图 —— 因为 `显示 = charlist[E(输入字)+5]`，
所以 `E(输入字) = charlist.index(显示字) - 5`，一张截图就能反读出 `M` 在需要的区间上的条目。

**建议探针串**：对每个目标字，取 `charlist` 位置 `i-25 … i+5` 的字符各排一段，并在段首加标记字便于定位。

## 九、坑（务必注意）

1. **不要用旧截图推显示字。** 不同构建的图集不同，同一个字被显示成的错字也不同。
2. **判 E 只能靠实测**（游戏显示 / 裁图集格子肉眼确认），不能靠任何推算模型。
3. **DXT3 编码必须复刻原图集的方式**（预乘灰度：颜色通道 ≈ 透明度）。用普通 DXT1 编码会把字渲染成透明 —— 早期踩过。
4. **小字截图容易读错**（我曾把 `螢` 读成 `垄`、把 `巧偶` 读成 `偶巧`）。**用户的读数 100% 可靠，优先采信。**
5. 改 vpp 前先完全退出游戏。
6. 汉化版第 2 句存在**结构性缺失**：`出`、`意`、`，` 的引擎索引超出 vf3 的条目数（N=2795），**没有格子可画**，整字消失；要补需要**扩展 vf3 表**（补 U/V 与记录项，指向图集空闲格子）。
7. 汉化版第 2 句还有 3 个**多出来的字**（`校`、`通`、`免`），位置都在 format 标签处，疑似标签字符被渲染 —— 未处理。

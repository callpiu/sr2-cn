## 1. 一句话说清这个项目在做什么

《黑道圣徒2》（Saints Row 2，2009 年 Volition 出品，无官方中文）的**简体中文汉化**，
以二进制方式改写游戏资源包 `patch.vpp_pc` 内的文本表（`le_strings`），
并配合 Juice Patch（社区修复/增强插件）与官方 DLC。

**汉化不是替换字体文件、也不是改 exe**，而是：
1. 在 `patch.vpp_pc` 里塞入中文字体资源 `fnt_chinese`（vf3 字形表 + DXT3 图集）与 `charlist_CH`（2795 字码表）；
2. 把各语言文本表（`static_CH` / `voice_script_CH` / `platform_pc_CH` 等）的文本槽改写成中文字符索引；
3. 引擎通过资源名 `_CH` 后缀识别中文资源，从而加载上述字体并显示中文。

**汉化能否显示，只取决于该界面文本是否走 `le_strings` 查表路径** —— 详见 §5。

## 4. 核心技术结论（读懂这几条就能接手）

### 4.1 `le_strings` 二进制格式（全部表通用）

```
头部 12B   [magic A84C7F73][ver u16][buckets u16][count u32]
桶表       buckets × [count u32][addr u32]   ← addr 指向【指针数组项】的绝对偏移
指针数组   count × u32                       ← 指向记录区绝对偏移
记录区     [ID u32][文本 slot...][0000]       ← 文本从 off+4 开始
```

- **文本是 slot 数组**，`slot = charlist 索引 + 0x20`；解码 `CL[slot - 0x20]`。
- `slot < 0x20` 是控制符（`0x0A` = 换行），**不能用 `chr(x)`**，要映射成占位符
  （本项目统一用 `'\x01C%02X\x01'`），打包时再写回原值。`0x20` 是空格，走正常路径。
- ★ **连 ASCII 也是 slot 编码**（'A' 在表里是 `0x0053`）⇒ **用 ASCII 字节去搜文本必然 0 命中**。
- 顺序扫记录时**前 2 个 slot 是 ID 不是文本**（会显示成 `??`），判短记录必须用 `slots[2:]`。
- 引擎按 32 位 hash **分桶查找**，不是线性扫描；桶结构坏了会返回 `!!unrecognized hash value`。
- 校验一律按 **头 12B / 文本 @off+4**（老外工具 sr2patch 的 HDR=16 / off+8 是错的）。

### 4.2 改写文本的两条安全路径

- **能缩短就缩短**（首选）：英文 slot 数 > 中文字数时，尾部补 `\x00` 提前终止，
  文件长度不变、桶表与指针数组都不用动：
  `新slot + b'\x00' * (len(旧) - len(新)) + b'\x00\x00'`
- **要变长就得扩容**：重排记录区 + 更新指针数组（桶表 count 不变）。v546 的
  `juiced_CH.le_strings` 就这么做的（762 → 800 B），改完**头部 12B 与桶表必须逐字节相同**。
- ★ **片段替换必须整记录重建**：解码整条 → 字符串替换 → 重新编码 → 补终止符。
  中途直接改 slot 数量会让其后的记录全部错位。

### 4.3 ★ 定位铁律：按 32 位 ID，不按文本

同一文本在不同 ID 含义可能完全不同。实例：「拳头」在 `static_CH` 有两条 ——
`AA0A5EB8` = `The Fist`（汉堡，要改）、`B45D9039` = `Fist`（别处，不能碰）。
正确流程：**英文表找目标 → 按 ID 对齐 CH → 按 ID 定位记录 → 断言现文本匹配 → 改 → 处理松散副本**。

### 4.4 ★ `Mods\` 下的 loose 文件优先于 vpp 内资源（v546 血泪教训）

- 引擎实际读的是 **`Mods\` 里的同名资源**，不是 `patch.vpp_pc` 里的那份。
  - `Mods\JUICED - Strings\juiced_CH.le_strings` 覆盖 patch 里的 `platform_pc_CH`；
  - `Mods\platform_PC_US.le_strings` 也覆盖同名表。
- **所以「某处文字错」第一步是 grep `Mods\`，确认引擎读哪一份**，改错文件 = 完全无效。
- ★ 官方 Juice 9.3.1 自带的中文表**本身就是整句乱码**（轻傲OPENSPY卧短 / 璃兵 / 重推 / 妈盆…），
  不能因为「官方自带」就认为正确。
- `Mods\` 里有 **57 个松散 `.lua`** 覆盖 VPP 内同名资源；
  `Juiced\logs` 或 `debug.txt` 里 grep `Possible loose file conflicts` 可列出冲突。
- ★ 界面漏出没翻译的 tag → **先 grep `Mods\*.lua`**，不要去查 le_strings：
  表是按 32 位 hash 查的，tag 文本根本不在表里。Juice 自造 tag 共 20 个，
  只有 `SUI_LAN_COOP_SP`（等待玩家）在正常流程必经，已改成官方 tag。

### 4.5 ★ 中文能不能显示：只看文本来源

| 文本来源 | 中文 |
|---|---|
| 走 `le_strings` 查表（`static_CH` / `voice_script_CH` / `platform_pc_CH` 等界面） | ✅ 正常 |
| **lua 字面量直传**（`vint_set_property(h, "text_tag", 文本)` 查表失败回落原文） | ❌ 必乱码 |

- 与「用了哪个字体样式名」**无关**（换样式只改字号）。字体样式 → 字体文件的映射表在 `SR2_pc.exe`。
- `juiced.ini` 的 `ForceLanguage` 可选值里**没有 CH**，中文完全是补丁注入的。
- 已实测失败并回滚的两条路：① 汉化 `Mods\city_load.lua` 的 46 条加载提示 → 乱码；
  ② 改 `common.vpp_pc` 里 `city_load.vint_doc` 的字体样式名（等长 16B 替换）→ 字号变了但仍乱码。
  **结论：加载画面提示保持英文**，要修得改引擎字体加载逻辑，风险过高、性价比不划算。

### 4.6 其他已知坑（速查）

| 坑 | 表现 | 处理 |
|---|---|---|
| 表外松散副本 | 同一记录在 vpp 里有 **2 份**（表内 + 表外，判据：前一个 word 是 `0000`） | 字节搜索得 2 处都要改 |
| 整文件 `buf.replace` | 把 10 个语言表（US/DK/SE/FR/JP…）一起汉化了（v541 事故） | 建 entry 区间表 + `owner(offset)`，只改目标表，收尾断言其它表字节不变 |
| 地图区域名 | 表里是**带尾空格的短记录**（`城 `=Suburbs），「区」由引擎自动补 | 改名 `城 `→`市郊` 得到「市郊区」；地名末字绝不能是「区」 |
| 同文双记录 | 改了"没效果" | 把同文所有记录一次全改（如「斯蒂尔沃特大学学生会」有 2 条） |
| 对白字幕 | 在 `voice_script_CH`，不在 `static_CH`；CH/US 的 ID **不通用** | 靠英文句子内容反查 |
| 坏字位 | 个别字短文本错、长文本正常 | 只能换同义词绕（清单见 §7） |
| 探针实验 | 等长替换 + 空格补齐 ⇒ 字数恒定，"没变化"没有判别力 | 探针必须**变长**，优先用 ASCII + 字母锚点 |
| DLC 格式 | 真 CJK 码点版 → 引擎按 slot 解越界，实机**显示空白** | 只能用 `_ref_DLC\dlc_ch_new.le_strings`（slot 编码版，`eedbc779`） |

### 4.7 内存扫描（判断"磁盘错"还是"渲染错"的唯一可靠手段）

- `F:\sr2-cn\ce_mini.py`：`ps` / `selfcheck` / `scan` / `dump ADDR`，纯 ctypes 调 WinAPI，免装 CE。
- ★ 必须显式声明 `argtypes`（指针一律 `c_void_p`），否则 64 位地址被截断、写入莫名失败。
- ★ 扫描上限用 `IsWow64Process` 判断：32 位 `0x7FFFFFFF`，64 位 `0x7FFFFFFFFFFF`
  （硬编码会让 64 位进程前 2GB 全 MEM_FREE）。
- ★ 搜 ASCII 必须用 **Array of byte**（内存里是 UTF-16**BE** `00 41`）；
  CE 的 String+Unicode 是 LE，必然 0 结果。汉字存的是 charlist 索引，搜 Unicode 也搜不到。
- 命中处往前 4 字节应是记录 ID；`enum_regions()` 返回三元组 `(base, size, protect)`。

## 6. 常见任务操作手册（SOP）

### 6.1 改一条界面文本（最常用）

1. `python sr2lib.py` 相关函数打开 `patch.vpp_pc`，先看目标表**是否被 `Mods\` 覆盖**（§4.4）。
2. 在英文表（如 `static_US.le_strings`）里按文本/区段找目标，记下 **32 位 ID**。
3. 在中文表里**按 ID** 定位记录，断言现文本 == 预期旧文本（否则停下，说明记错了）。
4. 解码整条 → 替换 → 重新编码（优先缩短）→ 写回。表外松散副本同样处理。
5. 用独立脚本回读校验；再与干净基线逐条比对，**差异应只有被改的那条**。
6. 打包 → **用户实机验收**。静态全绿 ≠ 能跑。

参考实现：`apply_v545.py`、`apply_v542_juiced.py`（前者改 vpp 内表，后者改 Mods 里的 loose 表）。

### 6.2 找"还没翻译"的文本

`python scan_untranslated.py`：CH 与 US 按同 ID 对齐，取「CH 文本 == US 原文」的记录 = 漏翻清单。
必须**按片段包含**扫（大量专名内嵌在长句里，如「Barrio 车站」「去 Barrio 喷涂鸦」）。

### 6.3 重新打一体化整合包（给别人用）

## 8. 三条铁律（转发给任何接手的人）

1. **绝对不要在 Steam 里点「验证文件完整性 / 修复文件」** —— 会把 `patch.vpp_pc` 还原成官方英文版，汉化全部丢失。
2. **不要再单独安装旧版 Juice** —— 会覆盖 `Mods\` 导致汉化失效；要装就用整合包里的流程。
3. **不要删 `Mods\dialog_box.lua` 和 `Mods\JUICED - Strings\juiced_CH.le_strings`** ——
   前者是「等待玩家」界面修复，后者是 OpenSpy 联机界面的重译版（官方自带那份是乱码）。

**判断"哪一层被还原"最快的办法**：用发布包 ↔ 游戏目录逐文件 md5 比对（`FILELIST.txt` 里有全量清单）。

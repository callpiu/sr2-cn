## 一、问题定义

《黑道圣徒 2》+ 官方繁中补丁，在「直升机突击」活动中，底部字幕显示乱码：

| 位置 | 应该显示 | 实际显示 |
|---|---|---|
| 字幕 1 | `兄弟們需要你的保護` | `使發光彈借歷復使發俱誘` |
| 字幕 2 | `兄弟們正要去進行交易，保護他們避免受到攻擊` | `使發光彈借步復友途螢交星點俱誘仙遞全句剝放擋` |

## 二、根因（已完整验证）

### 2.1 数据层面

```
patch.vpp_pc
  ├─ static_CH (le_strings, 469428 B)   ← 文本在此，内容【正确】
  │    hash 0x84F287ED = [format][color:green]兄弟們[[/format]需要你的保護
  │    hash 0x10AF1E62 = [format][color:green]兄弟們[[/format]正要去進行交易，保護他們避免受到攻擊
  │    槽位: 437, 994, 390, 1488, 2311, 562, 2534, 2275, 319, 1322, 2862, ...
  │
  ├─ charlist_CH (txt, 2838 项)          ← 槽位 -> 码点 的映射
  │    查表验证: charlist_CH[437-0x20] = 兄  ✓
  │
  └─ fnt_chinese (vf3_pc, N=2838)        ← 字形度量

common.vpp_pc
  ├─ fnt_body_n.vf3_pc  N = 224   ← ★ 只有 224 个 ASCII 字形
  └─ fnt_body_s.vf3_pc  N = 224   ← ★ 同上

textures.vpp_pc
  ├─ fnt_body_n  262144 B (512²)  ← ★ 英文图集
  └─ fnt_body_s  349520 B         ← ★ 英文图集
```

### 2.2 渲染层面

```
hud_msg.lua 第 104-106 行:
    o = vint_object_create("hud_msg", "text", region.anchor)
    vint_set_property(o, "text_tag", msg.text)
    vint_set_property(o, "font", "thin_overlay")     ← 字幕强制绑定此别名

exe @0x11d612 的别名注册：
    thin_overlay -> (fnt_body_n, fnt_body_s)         ← 纯 ASCII 字体

exe 导入表 @0xA7E694:
    D3DXCreateFontA  ← 原生 C++ 字幕路径用 D3DX 系统字体
```

### 2.3 结论

**这是游戏官方在 CJK 字幕上的原始缺陷**：
- 字幕走原生 C++ + D3DX 路径，与游戏的 `charlist_CH` / 字体图集**解耦**
- 引擎内部的「槽位 → 字形」映射代码有 bug，取到错误的字形
- **改任何游戏数据文件都无效**

## 三、已排除的方案（实测无效）

| 方案 | 改动内容 | 结果 |
|---|---|---|
| 1. 改文本 | `static_CH` 的 REC1/REC2 槽位 | ❌ 字幕无变化 |
| 2. 改文本 | 换成连续索引测试串（200~2800） | ❌ 字幕无变化 |
| 3. 改字体度量 | 全部 10 个 CJK 字体的 vf3 → N=2838 | ❌ 字幕无变化 |
| 4. 极端诊断 | 全部字体度量 → 单一字形（应显示成一串同字） | ❌ 字幕无变化 |
| 5. 三件套 | 度量 + 描述符 + **图集** 全换（fnt_body_n/s） | ❌ 字幕无变化 |
| 6. 改活动名 | `0x84C1140A` → `PANEL-A` | ❌ 面板无变化 |

**方案 4 是决定性的**：如果字幕用任何 `fnt_*` 资源，全换成同一字形后必然显示成一串相同的字。结果毫无变化 ⇒ 字幕**完全不使用**这些资源。

## 四、DLL Hook 方案（已实现）

### 4.1 原理

```
D3DXCreateFontA 被调用
      ↓ 我们的 hook 拦截
   拿到 ID3DXFont 对象
      ↓ 改它的 vtable 第 9 槽（DrawTextW）
   之后所有字幕绘制都经过我们的函数
      ↓ 匹配乱码字符串
   命中 -> 替换成 ASCII -> 转交原函数
```

**为什么用 ASCII**：该字体对 ASCII 渲染完全正常（面板的英文、数字都正确）。ASCII 替换是最可靠的方案。

### 4.2 关键匹配键

```
乱码1 (UTF-16LE):
  4F7F 767C 5149 5F48 501F 6B77 5FA9 4F7F 767C 4FF1 8A98
  = 使發光彈借歷復使發俱誘

乱码2 (UTF-16LE):
  4F7F 767C 5149 5F48 501F 6B65 5FA9 53CB 9014 87A2 4EA4
  661F 9EDE 4FF1 8A98 4ED9 905E 5168 53E5 525D 653E 64CB
  = 使發光彈借步復友途螢交星點俱誘仙遞全句剝放擋
```

替换为：
```
Your homies need your protection
Protect your homies from attackers
```

### 4.3 技术要点

**零导入设计**
```c
// 通过 PEB 遍历定位 kernel32，自解析导出表
__asm__ volatile("movl %%fs:0x30, %0" : "=r"(peb));   // PEB
ldr = *(BYTE**)(peb + 0x0C);                          // PEB->Ldr
// 遍历 InLoadOrderModuleList 找 kernel32
// 解析导出表拿 LoadLibraryA / GetProcAddress / VirtualAlloc / VirtualProtect
```
好处：**不需要任何 .lib**，绕过了 LLVM 包不含导入库的限制。

**入口点**
```c
extern "C" BOOL __stdcall _DllMainCRTStartup(HINSTANCE, DWORD reason, LPVOID)
// 被链接器设为 AddressOfEntryPoint，reason==1 时执行初始化
```

### 若 DLL 生效（字幕变成英文）
→ 完成。如需中文，可改为「用另一套可渲染的中文字体输出」，
   但那需要更深入地逆向字幕函数。

### 若 DLL 不生效
可能是 hook 目标不对（字幕不走 D3DXCreateFontA）。备选：

| 备选 hook 点 | 说明 |
|---|---|
| `ID3DXFont::DrawTextA` (vtable 第 8 槽) | 若游戏用 ANSI 版本 |
| `d3dx9_39!D3DXCreateFontW` | 宽字符版创建函数 |
| `ID3DXSprite::Draw` | 更底层 |
| `gdi32!TextOutA/W`、`DrawTextA/W` | 若用 GDI |
| `user32!DrawTextA/W` | 同上 |

**定位方法**：用 x32dbg 在游戏里对字幕文本下**内存断点**
（在字符串「使發光彈借步...」的 UTF-16 字节上下硬件访问断点），
命中的调用栈就是真正的绘制函数。

## 十、关键教训

1. **数据的正确性 ≠ 渲染的正确性**。`static_CH` 里的文本完全正确，
   但引擎的槽位→字形映射有 bug，导致显示错误的字。

2. **「同一槽位显示不同字」是决定性线索**。
   槽位 390 在 REC2 位置 2 显示「光」，位置 14 显示「誘」——
   证明屏幕显示不是槽位的纯函数，排除了所有「换表/偏移」类方案。

3. **全量诊断优于逐个猜测**。
   把全部 10 个字体度量换成单一字形，一次实验就排除了整类假设。

4. **CJK 位图诊断要小心看图**。
   我一度把「兄弟們」误读为「光彈借」，导致后续推导全错。

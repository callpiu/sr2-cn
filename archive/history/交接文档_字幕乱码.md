## 1. 问题定义

### 现象
- 位置：屏幕**中下方**的对白字幕（subtitle），**不是** HUD 面板。
- 同一画面里两者并存且表现相反：
  - 左上角面板「直升机突击 / 已完成停靠 0/4 / 面包车耐久 LVL2」→ **中文正常**
  - 中下方字幕「你的弟兄们需要你的保护」→ **乱码**

### 乱码样本（正确 → 实际显示）

| 正确 | 实际显示 |
|---|---|
| 你的弟兄们需要你的保护 | 任璨偶巧位雄衡任璨伪该 |

## 2. 已验证为「正确」的事实（硬证据，勿重复验证）

### 2.1 数据层全部正确

| 环节 | 结论 | 验证方式 |
|---|---|---|

| 汉化图集 `fnt_chinese.g_peg_pc` | 4194304 B = 2048² DXT3；**cell k 严格等于 `charlist_CH[k]`**（65 列、步距 31、偏移 1） | 解 DXT3 + 目视核对 18 格：cell 33=A、336=任、354=伪、362=位、371=你、391=保、410=偶、422=兄、967=巧、1035=弟、1190=护、1784=璨、1836=的、2268=衡、2296=要、2342=该、2656=雄、2667=需 |
| `fnt_chinese.vf3_pc` | N=2795，U/V 表「记录 i → 格子 i」 | 结构解析 |
| 两份图集一致性 | `patch.vpp_pc` 与 `textures.vpp_pc` 的 `fnt_chinese` **md5 相同**（`340340761dda…`） | md5 比对 |

**⇒ 结论：字符串记录、字符表、图集、vf3 四层都没问题。问题不在「文本处理流程」。**

### 2.2 渲染路径的结构性差异（关键线索）

- `hud_msg.lua`（`patch.vpp_pc` 内，7817 B）第 106 行：
  ```lua
  HUD_REGION_SUBTITLES = 3
  Hud_msg_subtitle_text = { scale = 0.7, wrap_width = 0 }  -- Needs to match subtitles.cpp
  ...
  vint_set_property(o, "font", "thin_overlay")
  ```
- **全量扫描所有 lua，只有 9 处 `font` 赋值**：
  - `hud.lua`：2 处（都是 radial_menu）
  - `hud_msg.lua`：1 处（**字幕**，`thin_overlay`）
  - `pause_menu.lua`：4 处
- **面板文字在 lua 层完全不设字体**，靠 vint_doc 模板默认；
  **字幕是唯一「lua 动态创建 + 显式设 font」的对象。**
- 注释 `Needs to match subtitles.cpp` ⇒ 字幕由**原生 C++ `subtitles.cpp`** 绘制，
  与 vint 渲染器不是同一条路径。

## 3. 已排除的假设（**不要重复尝试**）

| # | 假设 | 排除方式 / 结果 |
|---|---|---|
| 1 | 字幕用 `jap` 字体 | 乱码字「伪/该/璨/巧/们/护/你」不在 `charlist_JP`(1980 项)、也不在 `JPCharList` |
| 2 | 引擎用官方 charlist 译码 | 0/9 命中 |
| 3 | 5 张语言表任意组合映射 `X.index(Y[i])±d` | **0 命中**（LC/LO/JP/JPCharList/SK 两两组合） |
| 4 | 简单网格公式 `j=(R0+(i-A)//C)*65+((i-A)%C)` | A∈[0,400)、C∈[58,72) 全空间，**无 ≥3 命中** |
| 5 | charlist 排序异常 / 二分查找被破坏 | 汉化表严格递增、2795 个唯一值 |
| 6 | 图集文件差异（引擎读了另一份） | patch 与 textures 的 `fnt_chinese` md5 相同 |
| 7 | 模板匹配定位字形 | 汉化黑体 vs 官方衬线体，相关度峰值仅 0.4~0.9，不可靠 |
| 8 | 松散文件覆盖（`Mods\static_CH` / `charlist` / `vint_proj`） | `debug.txt` 的 `[LOOSE_FILE]` 372 条中，lua 仅 6 个，且不含上述文件 |
| 9 | 「面板走默认字体，所以字体没问题」 | **实测否证**：方案 A 注释掉 font 行后字幕整条消失 ⇒ vint text 不设 font 就**完全不渲染** |
| 10 | 官方图集是另一套布局所以能反推 | 官方图集 = 行 0-1 Latin(0..256)、行 2 起 CJK 从 257 起、66 列；与汉化布局恰好都是从序号 0 开始的同构网格，无法据此推出映射 |

### 关键「反常识」事实（此前所有弯路的原因）

1. **`font` 属性只接受「别名」**（`thin` / `thin_overlay` / `header_n` / `header_n_overlay` /
   `bodyital_overlay` / `debug`），**不接受字体资源名**。
   实测：写成 `fnt_chinese` ⇒ **所有字幕整条消失**（不是乱码）。
2. 改 `sr2.vint_proj` 的 `<font_info><alias>` → **无效**
3. 改 vf3 / 图集 / pegs 描述符 → **无效**
4. 改 exe 字体名表 → **无效**（见下）

## 5. 破译的格式（可直接复用）

### 5.1 `le_strings` 格式

```
@0     magic  0xA84C7F73
@4     ver    u16  (=1)
@6     buckets u16
@8     count  u32
@12    bucket 表：buckets × 8 B
       每项 = [count u32][offset u32]
       offset = 12 + buckets*8 + 累计记录数*4
       （即 pointer array 里的绝对字节偏移）
@12+buckets*8
       pointer array：count × u32（绝对文件偏移，指向记录）
记录 = [id1 u16 LE][id2 u16 LE] + u16 大端槽位... + 0x0000 终止
槽位 = charlist 索引 + 0x20   （不是 Unicode 码位）
字面标签（[format] 等）也是 ASCII 码位 − 32
```

**验证方法**：`count` 与 `buckets` 逐项累加，offset 必须严格连续递增。

### 5.2 ⚠️ T7 崩溃的原因（重要教训）

重建 le_strings 时，**pointer array 的顺序必须与 records blob 的物理顺序一致**。

错误做法：
```python
# 按 hash 分组重排 pointer array，但 records_blob 仍按原始顺序打包
# => pointer 指向错位的记录 => 引擎崩溃
```

正确做法（二选一）：
1. **保持原始顺序**：records_blob 与 pointer array 用同一序列；
2. **最小改动**：不动 header / bucket table / pointer array，
   只把要改的记录**追加到文件末尾**，再改**对应那几个 pointer**（T8 的做法）。

### 5.3 VPP 容器格式

```
magic  5 B : CE 0A 89 51 04
@5+0x14F  : num i32, container_size i32, len_offsets i32,
            len_filenames i32, len_extensions i32
条目表 @0x800，28 B/条：
  +0  name_off  u32   → 指向 names 区（相对偏移）
  +4  ext_off   u32   → 指向 extensions 区（0 = 无扩展名）
  +8  ?         i32
  +12 body_off  i32   → 相对 data_start 的偏移
  +16 size      i32
names_at   = ((0x800 + len_offsets) & 0xFFFFF800) + 0x800
ext_at     = ((names_at + len_filenames) & 0xFFFFF800) + 0x800
data_start = ((ext_at + len_extensions) & 0xFFFFF800) + 0x800
```

**「追加式替换」安全**：把新 body 写到文件末尾（对齐 0x800），
改条目的 `body_off` 与 `size`，再更新 `container_size`。原数据保留在文件里成为死数据，引擎不会读。

## 7. 生成物清单（`F:\sr2-cn\`）

### 7.1 格式库（**最该复用的部分**）

| 文件 | 功能 |
|---|---|
| `sr2lib.py` | **核心格式库**：<br>• `Vpp` 类：`entries()` / `read()` / `find()` / `replace_body_appended()` / `save()`<br>• `parse_charlist` / `build_charlist`（注意：`parse_charlist` 依赖 `count=` 头，对**无头**的汉化版会抛 `AttributeError`）<br>• `parse_vfnt` / `build_vfnt`（注释说 0xD0 头 + N×16，**实际是 0xBC 头 + N×24**，注释有误）<br>• `dxt3_decode` → `(rgb h,w,3, alpha h,w)`、`dxt3_encode`（**预乘 alpha 灰度 DXT1 三色模式**） |
| `tools\sr2lib.py` / `tools\sr2patch.py` | 早期版本（含 `.le_strings` 读写与单元解码） |
| `_HL2_cl.py` / `_HL4_rec.py` | **十进制 charlist 解析**（`re.findall(rb'\d+', buf)`）与 le_strings 记录解析的干净实现，建议直接抄 |

> **踩坑记录**：
> - charlist 是**十进制、换行分隔**，不是十六进制。用 `[0-9A-Fa-f]{2,6}` + `int(x,16)` 会得到错值
> - 汉化版 charlist **无 `count=` 头**，官方版有头（`count=2838`）
> - `Vpp.entries()` 返回 **dict 列表**（用 `e['name']`，不是对象属性）
> - 图集条目 `ext` 为**空字符串**，`find("fnt_chinese", "g_peg_pc")` 会返回 None，要传 `find("fnt_chinese", None)`
> - `dxt3_decode` 返回**元组** `(rgb, alpha)`

### 7.5 关键地址（SR2_pc.exe 无 ASLR，绝对地址）

| 地址 | 含义 |
|---|---|
| `0x7F4F60` | `compress_char`（Unicode → 槽位）。**已证实是加载期调用**（硬件断点：100 秒 0 触发），不是渲染期 |
| `0x7F4430` | `loadcharlist`（被 Juiced 挂钩，首字节 `E9`） |
| `0x02528B2C` | `cc_list` 指针（`{u16 unicode; u16 compressed}[]`） |
| `0x02528B30` | `num_cchars` |
| `0x11d290` | 语言→字体 switch 表（`[0xE8C470]`）：`==3 → jap`、`==0x0D → fnt_chinese`、`==0x0B → fnt_korea`、`==9/10/12 → fnt_cz`、default → `fnt_body_n/s/ital/head` |
| `0x9e0fc0` | 字体字符串池（`.rdata`，RVA == 文件偏移）：`jap`@cc、`fnt_chinese`@d0、`fnt_korea`@dc、`fnt_cz`@e8、`fnt_cz_s`@f0、`fnt_body_n`@fc、…、`thin`@60、`thin_overlay`@68、`header_n`@78、`header_n_overlay`@84、`bodyital_overlay`@98 |
| `0x11d612`~`0x11d679` | 别名注册：`thin`→(fnt_body_n, -1)、`thin_overlay`→(fnt_body_n, fnt_body_s)、`header_n`→(0xE98A6C, -1)、`header_n_overlay`→(0xE98A6C, 0xE98A68)、`bodyital_overlay`→(fnt_bodyital_n, fnt_bodyital_s) |

> 注：`0x11d290` 的 switch 说明「中文模式下确实加载 `fnt_chinese`」，
> 但它**不能**解释字幕乱码 —— 所有别名都拿到了含 CJK 层的复合字体。
> 这也是为什么「换别名」不是优先方向。

## 8. 仍未解决 & 给接手者的建议

### 8.1 唯一阻塞点

**`subtitles.cpp` 原生渲染路径的「槽位 → 字形格」映射公式未知。**

9 组 (i→j) 差值 `-35 -52 -625 +545 +30 -11 -28 -35 -52 -37 +1152`
不符合任何已测模型。

### 8.2 优先排查方向（按推荐顺序）

1. **先确认 `Mods\hud_msg.lua` 是否生效**（§6.2）。
   它 14018 B，而 `patch.vpp_pc` 内那份只有 7817 B，明显是**改过的版本**。
   对比两者的 `font` 行，并看 `debug.txt` 里 `[LOOSE_FILE]` 是否出现 `mods\hud_msg.lua`。
   **如果 Mods 那份生效，那么所有改 `patch.vpp_pc` 内 `hud_msg.lua` 的尝试（T5/T6）都白做了。**

2. **确认字幕文本的真实来源。** T9 已证明：等长改写 `patch.vpp_pc` 的 `static_CH`
   对画面**零影响**。需要查：
   - `Mods\` 下的 `static_*.le_strings` / `platform_PC_*.le_strings`（**注意：没有 `static_CH`**）
   - `DLC\Text\dlc_ch.le_strings`（松散文件，49924 B）
   - `voice_script_CH`（4069 条，但按当时 charlist 解码**不含**「弟兄们」）
   - 是否存在**缓存**（Juiced 的 `data\DFEngine\cache\`）

3. **用调试器抓渲染路径**（README 的结论仍然成立）：
   > **不要在文本处理流程里找字形布局，要去字形渲染流程里找。**
   >
   > `compress_char` 是**加载期**调用，不是渲染期。
   > 建议从 `IDirect3DDevice9::CreateTexture` / `D3DXCreateTextureFromFileInMemory` /
   > `DrawText` 类函数入手，找**接收槽位并输出 UV 矩形**的那个函数。
   > 现成工具：`sr2_hwbp.exe`（改 `ADDR_TARGET` 即可断在任意地址）。

4. **不要再用离线渲染「猜」字体。** T1~T6 全部是离线看着合理、游戏内无效。
   引擎行为只能由**游戏内实测**确定。

### 8.3 如果只想「让字幕不丑」

在确认文本来源后，把受影响记录改成**纯 ASCII 英文短句**是最稳的降级
（T9 的等长覆盖写法可直接复用，见 `_IU1_applyB_inplace.py`）——
但**前提是先找到真正被读取的那份文件**，否则改哪里都没用。

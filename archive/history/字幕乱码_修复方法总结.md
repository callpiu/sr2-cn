> 原版备份：`F:\sr2-cn\_backup_VANILLA\patch.vpp_pc.vanilla_20261017`（`805ab98e…`）

## 一、根因（一句话）

**游戏字体图集 `fnt_chinese` 里字形的排列顺序，和随包的 `charlist_CH.txt` 对不上**（本机原版整体差 **5** 个位置）。

不是编码问题、不是文本问题、不是汉化补丁问题 —— 原版就有。官方数据自己不一致。

### 证据链
1. 文本本身是对的：`static_CH` 里 `84F287ED` = `你的兄弟們需要你的保護`，内存里的槽位也一致
2. 乱码是**逐字确定性替换**（你→使、的→發、兄→光、弟→彈、們→借、需→雇…），跨不同句子完全自洽
3. 图集第 325 格 = 「何」（= `charlist_CH[330]`）、第 333 格 = 「侈」（= `charlist_CH[338]`）
   ⇒ **图集第 k 格 = `charlist_CH[k + 5]`**
4. 改文本 / 改 charlist / 改启动参数 / 改系统区域 —— 全部无效（因为问题在图集本身）

## 二、关键换算关系（本项目逐个像素验证过）

| 项 | 值 |
|---|---|
| 图集文件 | `patch.vpp_pc` → `fnt_chinese.g_peg_pc`，4194304 字节 = **2048×2048 DXT3** |
| 坐标表 | `patch.vpp_pc` → `fnt_chinese.vf3_pc`，68300 字节 |
| 字符表 | `patch.vpp_pc` → `charlist_CH.txt`（2838 项，按 Unicode 升序） |
| **格子坐标** | **`(U[k], V[k])` 就是第 k 格的左上角像素坐标**（vf3 尾部两个数组，`U` 在 `0xD0 + N*16`，`V` 紧跟其后 `N*4`） |
| 格子尺寸 | 31×31，字形墨迹约 22×22 居中 |
| 图集偏移 | 本机原版 `OFFSET = 5`（图集第 k 格 = `charlist_CH[k+5]`） |

## 三、修复原理

对每个乱码字 `c`（截图里看到它被显示成了 `d`）：

```
源格 src = charlist_CH.index(c) - OFFSET     # 这一格装着 c 的正确字形
目标格 dst = charlist_CH.index(d) - OFFSET    # 引擎实际取用的那一格（现在装着错字）
把 src 格的 31×31 像素搬进 dst 格，只重编受影响的 DXT3 块
```

**为什么可行**：不需要知道引擎为什么取错格子，只要把「它会去取的那一格」换成正确字形。
副作用极小（只动几十个格子），且对所有分辨率、联机都正常，不需要任何注入。

## 七、坑与注意事项

1. **不要用旧截图推的 J 值**。不同构建的图集不同，同一个字被显示成的错字也不同。
   （本项目就踩过：`行` 在旧构建里显示成「貌」，在现在的原版里显示成「螢」）
2. **判定「目标格」必须双重确认**：① 截图里读出错误字 → ② 裁原版图集该格，肉眼确认它确实是那个错字。
3. **`charlist_CH` 里没有的字**不能用这套办法（比如简化字在繁体表里可能不存在），要单独处理。
4. **改图集后不要动 vf3**。格子坐标不变，只换格子里的图形，所以 vf3 一个字都不用改。
5. **DXT3 编码要复刻原图集的方式**：本图集是「预乘灰度」——颜色通道 ≈ 透明度，
   用普通 DXT1 编码会把字渲染成透明（本项目早期踩过这个坑）。`sr2font.enc_block` 已按正确方式实现。
6. **游戏运行中不要替换 vpp**，先完全退出。

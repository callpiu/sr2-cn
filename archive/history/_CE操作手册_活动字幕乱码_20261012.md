## 1. 为什么 ASCII 探针对 CE 特别有用（原理，先看这段再搜）

le_strings 里字符按 **u16 大端（BE）** 存储：

| 字符类型      | slot 值                       | 内存字节（BE） |
| --------- | ---------------------------- | -------- |
| ASCII `[` | 0x5B                         | `00 5B`  |
| ASCII `f` | 0x66                         | `00 66`  |
| 汉字 你      | charlist 索引 371 + 0x20 = 403 | `01 93`  |

于是：

- **ASCII 部分**在内存里就是 `00 41 00 42 …`，等价于 **UTF-16BE 的 "ABCDEFGHIJK"**。
- **汉字部分**存的是 charlist 索引，**不是 Unicode 码点**，所以搜中文 Unicode **搜不到**（这正是"外部文档说文本不在表里"的根因）。
- CE 的 String+Unicode 扫描是 **UTF-16LE**（`41 00 42 00`），跟内存里的 BE 顺序相反 ——  
  **所以搜 ASCII 请务必用 Byte Array，别用 String+Unicode**，否则必然 0 结果并误判为"不存在"。

> 反过来：如果游戏在渲染前已把 slot 转换成真正的 Unicode，那 String+Unicode 就能搜到。  
> 两种都试，就能判断游戏是"直接拿 slot 渲染"还是"先转 Unicode"。**这本身就是一条关键信息。**

### ⚠ 补充陷阱：同一份 ASCII 数据会被两种字节序【各命中一次】

这条是 2026-10-12 晚用脚本实测发现的，会影响你对"命中几处"的判断：

ASCII 字符的 UTF-16 必有一个字节是 `00`：

```
'['   BE = 00 5B        LE = 5B 00
```

于是一段 BE 数据 `00 5B 00 66 00 6F …`，**从下一个字节读**，恰好就是 LE 的 `5B 00 66 00 6F …`。  
所以：搜 BE 和搜 LE **会在同一份数据上各命中一次**，两个地址只差 1 字节。

这还不是"谁真谁假"的问题——**它们在信息论上不可区分**：
`0x00 + LE字符串` 拼出来的字节，跟 `BE字符串` 的字节**逐字节完全相同**。
所以别纠结哪个是真的，只在乎一点：**它是一份，不是两份**，别据此误判"存在第二数据源"。

**成立条件**（两条都满足才会错位）：

1. 目标是**纯 ASCII** 串（汉字不成立：任 U+4EFB 的 BE = `4E FB`，两字节都非零，错位后凑不出 LE 的形式。实测确认：BE 存储的汉字搜 LE 命中 0 处）
2. 数据的**前一个字节恰好是 0x00 且可读**（页首分配时前一字节落在别的页，就不会错位）

**对你的影响**：

- 搜 `[format][color:green]` 这类标签时，命中数可能翻倍 → **除以 2 才是真实份数**
- 搜**中文**（`任璨偶巧位`）**完全安全**，不会错位，命中几处就是几份
- 本项目的 `ce_mini.py` 已内置甄别，会在命中地址旁自动标注"同一份数据的另一种字节序解读"

## 2. 实验 A：定位内存中的中文表（最高优先级）

1. 启动游戏，进入任意一个能触发活动字幕的界面（或直接进主菜单也行，表可能已加载）。
2. CE → 打开进程 `SR2_pc.exe`。
3. 首次扫描：
   - **Value Type = Array of byte**（不是 String）
   - Hex 打勾，把上面那串 `[format][color:green]` 的 BE 字节粘进去
   - 若嫌长，可用更短的 `00 72 00 65 00 65 00 6E 00 5D`（= "reen]"）
4. 看结果数量：
   - **1~几个结果** → 记下地址 A。这就是中文表在内存里的位置。
   - **0 结果** → 改用 String + 不勾 Unicode 搜 `[format]`（纯 ASCII 单字节），  
     或者改搜 `Color:Green`（注意大小写），或搜 `homies`。  
     仍 0 → 表尚未加载到内存（需要真正进入活动才会加载，进活动后再扫）。

### 找到地址 A 之后立刻做两件事

**A-1. 确认加载的到底是不是我们改的那份**  
在 CE 里右键地址 A → `Browse this memory region`，往前看 4 字节应是记录 ID  
（`ED 87 F2 84`，即 hash `0x84F287ED` 的 LE 存储），往后应能看到  
`弟兄们` 的 slot `04 2B 01 C6 01 6C`。对得上 → 铁证游戏读的就是我们改的表。

**A-2. 看是谁在用它（定位渲染路径）**  
右键地址 A → `Find out what accesses this address` → 触发一次活动字幕 →  
看列出的指令属于哪个模块。

- 若是 `SR2_pc.exe` 主模块 → 主程序渲染
- 若是 DFEngine.dll / 某个 lua 相关模块 → 记下偏移，可进一步查字体绑定

## 3. 实验 B：内存实时改 slot，直接读字形映射（核心，最快）

这是 CE 相对"改文件+重启"的最大优势：**不用退出游戏**。

1. 先按实验 A 找到地址 A。
2. 地址 A 开始的字节就是 REC1 文本：
   ```
   A+0  : 01 93   <- 你  (charlist 索引 371 + 0x20)
   A+2  : 07 4C   <- 的  (索引 1836 + 0x20)
   A+4  : 00 5B   <- [
   ...
   ```
3. 把 `A+0` 的两个字节改成你想要的 slot（BE），然后**重新触发一次活动字幕**  
   （退出活动重进，或让提示再次弹出），看屏幕上这个位置显示什么字。
4. 记录：`slot 0x0193 → 屏幕上显示「任」`（举例）。

**建议测的 slot 值**（这些是修复真正需要的点，不要盲目全表扫）：  
我们要知道「你、的、弟、兄、们、需、要、保、护、出、去、谈、几、笔、生、意、他、免、遭、袭、击」  
这 21 个字在 HUD 字表里的正确索引。

做法：逐个把目标字设成不同 slot 试，看屏幕是否显示成它自己。

- 若某个 slot 值让屏幕显示「你」→ 那个值就是「你」在 HUD 字表的正确 slot。
- 捷径：先试 slot = 371+0x20（charlist 原值）附近 ±50 的范围，  
  若字表只是整体偏移/局部错位，命中率很高。

**批量技巧**：CE 里可以一次改多个字节。把 REC1 前 11 个中文字位同时改成  
不同 slot，一次截图就能读出 11 个映射，效率翻 10 倍。

## 4. 实验 C：搜乱码 Unicode，检验「第二数据源」假说（30 秒）

外部文档声称"字幕是运行时产物、不在 static_CH 里"。用 CE 可以直接证伪：

1. CE → Value Type = **String**，勾选 **Unicode**
2. 搜索 `任璨偶巧位`（用户看到的乱码前 5 字）
3. 判定：
   - **0 结果** → 内存里根本不存在这串中文，乱码只是**渲染期把 slot 映射错字形**的产物  
     → 印证本文档结论，问题在字体/字表配对
   - **有结果** → 内存里确实有这份文本 → 存在第二个数据源，记下地址，  
     用 `Browse memory region` 看它在哪个模块/哪个文件映射区

补充搜：`Your homies need your protection`（String，不勾 Unicode）  
—— 若搜到，说明 static_US 也被加载了，可对比中英两表地址差。

## 6. 配合使用的探针脚本（不重启游戏时用 CE，重启时用它）

```bash
cd F:/sr2-cn
set PY="C:/Users/ezplayer/.workbuddy/binaries/python/envs/default/Scripts/python.exe"

%PY% probe_ascii.py show      # 看当前内容
%PY% probe_ascii.py ascii     # 装纯 ASCII 探针（REC1=ABCDEFGHIJK, REC2=A..V）
%PY% probe_ascii.py ruler     # 装标尺探针：A你B的C弟D兄E们F需G要H保I护J
%PY% probe_ascii.py restore   # 还原到最近一次探针前
%PY% dump_probe_bytes.py      # 导出当前 REC1 字节，给 CE 搜
%PY% healthcmp.py             # 与 v532 逐条对比，确认表没被改坏
```

**ruler 探针是一次拿全映射的最佳办法**：字母当位置锚点，屏幕上形如  
`A?B?C?D?E?F?G?H?I?`，把每个字母后面那个汉字抄下来即可，**彻底消除手写转录误差**  
（之前用户手写转录的对齐已被证明不可靠，"护→该"这类映射对不上）。

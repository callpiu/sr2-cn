**vf3 真实结构（本轮修正）**：头部 **0xBC（188 字节）**，不是 0xD0。

```
文件大小 = 0xBC + N*16 + N*8      # 严丝合缝，已反证
U 数组 @ 0xBC + 16N              # 之前记的 0xB3FC 是数组中部，common 实际 0xB21C
V 数组 @ U 之后 4N
记录 = (字宽, 字宽, 0, 65535)，field0/1 值域 patch 17-30 / common 7-30，**无任何码点字段**
```

`sr2lib.py` 里 0xD0 的假设会让记录整体错位 20 字节。

### 2.3 ★★★ 引擎里找到了字表全局变量与相关代码

来自旧脚本 `_day_2026-10-07/02_诊断脚本/a5_common.py` 的情报（本轮才用上）：

```
CHARLIST_PTR_VA = 0x02528B2C   # 字表指针
NUM_CCHARS_VA  = 0x02528B30   # 条目数（当年实测 2838）
```

字表是 **u32 数组：低 16 位 = 码点，高 16 位 = kerning/宽度索引**。  
⚠️ 这解释了此前「内存无字表」的误判——**我搜的是 u16 精确模式，而它是 u32 且高位非零**。

反汇编（ImageBase = 0x00400000，无 ASLR，**静态 VA 即绝对地址**；PE32 的 ImageBase 在 opt+**28** 不是 +24）找到两个关键函数：

- **`0x007F4E30` 校验函数**：对每个 UTF-16 字符，从索引 0 开始**线性扫 charlist**，`charlist[i].low16 == ch` 则通过，`>` 则判失败并替换为 `'_'`(0x5F)。  
  ⇒ **它假定 charlist 已排序**。patch 的 charlist_CH 确实排序 ⇒ 中文界面正常。  
  ⇒ **若 HUD 走的是 common 那套未排序/不同内容的表，同一算法就会返回错位或下划线**。
- **`0x007F4EE0` 附近函数**：出现 `lea edx, [edi + 2]`，**从每条 4 字节字表项的 +2 偏移（高 16 位）读码点**，与校验函数读 +0（低 16 位）**读的是不同半字**。这两个半字含义不同，可能正是「同一索引两种字形」的直接原因。**此函数尚未完整反汇编，是下一步首要目标。**
- 引用字表全局的代码密集簇：`0x3F4E00–0x3F5200`（VA），以及 `0x7F4400–0x7F4700` 一带。

### 2.4 本轮已排除（不要再重复劳动）

| 假说                                     | 结论      | 证据                                            |
| -------------------------------------- | ------- | --------------------------------------------- |
| H2b：HUD 把 charlist 索引直接当 common 字形索引   | **证伪**  | common[332]=作（非位）、common[371]=健（非任）           |
| 排序键错位（键排序了值没排）                         | **证伪**  | 9/9 全不吻合                                      |
| 简单二分查找                                 | **证伪**  | 多种二分变体均不复现                                    |
| T 是「按码点排序的位移表」                         | **证伪**  | T[371]=4EFB > T[391]=4F2A，而 371<391 ⇒ 不可能升序   |
| 哈希碰撞（乱码串作为某条记录存在）                      | **证伪**  | R1/R2/R3 全 0 命中（自检串 31 命中 ⇒ 扫描器可靠）            |
| T 存在磁盘（u16/u32 数组 / 宽字符文本 / slot 形式记录） | **证伪**  | 2904 个文件 × 4 种编码全 0 命中                        |
| T 存在内存（u16/u32 数组，基准无关，stride 2/4）     | **证伪**  | `mem_scan3.py` 修复相对偏移 bug 后重扫仍 0 命中（**含正对照**） |
| vf3 内嵌码点                               | **证伪**  | 记录只有字宽，无码点字段                                  |
| 字表在内存但我漏扫了 >2GB                        | **已排除** | 已按 4GB 全空间重扫（32 位 + LAA，进程已用 2.07GB），仍 0 命中   |

**综合推论**：错位映射 T 既不是静态数据表，也不是内存中的简单数组。它要么 (a) 由代码从某两张表的差异**计算**产生，要么 (b) 存放在**非数组结构**（哈希表/打包结构）里，要么 (c) 上面那条 —— **slot→码点转换其实是正确的，错误发生在「码点→字形查找」这一步**（用错/未排序的表做查找），宽字串「任璨偶巧位」是由错误字形索引**反查**得到的。

## 5. 铁律提醒（血泪教训）

- 二进制改动**最终验收 = 用户实测**。静态全绿 ≠ 能跑。卡住 >2h 就重审最基本前提。
- 判显示先看**像素**（用正确解码器）；判格式先 hex dump；别假设「跟之前一样」。
- **看图认字不可靠**（曾把郊看成邓、伙看成仪、把 裡 看成 里）——认不准必须渲染大图逐字核对或问用户。**跨字体 NCC/L1 数值比对已被证完全无判别力，别再用。**
- 探针实验必须**变长**；探针优先用 **ASCII**（ruler 探针 `A你B的C弟D兄E们…` 可一次读全映射）。
- CE 搜索编码陷阱：le_strings 按 u16 **BE** 存 ⇒ 搜 ASCII 必须用 **Array of byte**，用 String+Unicode 必 0 结果。
- 定位一律用**字节级搜索取绝对偏移**；★ **整文件偏移 vs blob 相对偏移极易混**，索引 vp.data 时用文件绝对偏移。
- PE32：ImageBase 在 optional header **+28**；无 ASLR 时静态 VA = 绝对地址。
- try/except:continue 会把「格式不兼容」假装成「不存在」→ 搜索必须先在正样本上自检。
